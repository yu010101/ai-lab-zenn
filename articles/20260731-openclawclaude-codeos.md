# OpenClaw×Claude Code連携実践｜経営OSと自律開発をつなぐ具体的ワークフロー

## はじめに：なぜ「思考」と「実行」を分離するのか

AIエージェントを実務で使い倒していると、ある壁にぶつかる。1つのAIに「考えること」と「手を動かすこと」を両方任せると、どちらも中途半端になるという壁だ。

長期記憶や意思決定の文脈を保持しながら経営判断的な指示を出す層（OpenClaw）と、その指示を受けてファイルを編集し、コマンドを実行し、テストを回し、デプロイまで持っていく層（Claude Code）――この2層に役割を分離すると、AI活用は急に「実務で回るもの」に変わる。

本記事では、筆者が実際に運用している「OpenClaw（思考・記憶・指示）×Claude Code（開発・実行）」の連携パターンを、具体的なコマンドとともに紹介する。2026年8月現在、複数プロダクトを1人〜少人数で回す個人開発者・フリーランスエンジニアにとって、この構成は現実的な選択肢になりつつある。

## OpenClawとClaude Codeの役割分担

まず前提を整理する。

| レイヤー | 役割 | 具体的な機能 |
|---|---|---|
| OpenClaw | 思考・記憶・指示 | 経営判断のペルソナ分割（CEO/CFO/CTO/COO/CMO）、永続メモリ、意思決定の文脈保持、タスクの優先順位付け |
| Claude Code | 開発・実行 | ファイル編集、Bashコマンド実行、git操作、テスト実行、デプロイ、サブエージェントへの委任 |

ポイントは、OpenClaw側は「何をすべきか」を判断し、Claude Code側は「どうやるか」を黙々と実行する、という非対称な関係にあることだ。経営判断とコード実装を同じコンテキストで混在させると、どちらも精度が落ちる。分離することで、それぞれが得意な粒度の思考に専念できる。

## アーキテクチャの実際：ペルソナ型マルチエージェント経営OS

筆者の環境では、OpenClaw側を「CEO/CFO/CTO/COO/CMO」という経営ペルソナに分割し、それぞれが担当領域のデータソースと接続されている。

```
/ceo    → CFO/CTO/COO/CMOの報告を統合し経営ダッシュボードを生成
/cfo    → freee連携で財務データ取得・PL生成・仕訳計上・未決済管理
/cto    → プロダクト群のヘルスチェック、技術スタック管理、開発優先度提案
/coo    → タスク進捗・クライアント管理・営業パイプラインの横断管理
/cmo    → GA4/Google Ads/GSCデータを統合したマーケティング戦略提案
```

実際のコマンド例を挙げる。

```bash
# 技術的な健全性チェックを毎朝の定例にする
/cto health

# 財務の未決済項目を確認する
/cfo 未決済

# クライアント状況を横断的に把握する
/coo clients

# 全体ダッシュボードで意思決定材料を揃える
/ceo
```

これらはただのレポート生成ではない。CTOペルソナが「このプロダクトは技術的負債が閾値を超えている」と判断すれば、その指示がClaude Code側の実行タスクに変換される、という流れになっている。つまりOpenClawは「気づいて優先順位をつける」層であり、実際に手を動かすのはあくまでClaude Codeだ。

## 開発パイプラインでの連携：監査→設計→実装→検証→デプロイ

もっとも効果を実感しているのが、コードベースの監査から実装、デプロイまでを一気通貫でつなぐパイプラインだ。

```bash
# 1. コードベース全体を大規模コンテキストで監査
/analyze
# → アーキテクチャ・セキュリティ・パフォーマンスの観点でレポート生成

# 2. 画面/機能の設計書を生成
/spec
# → コンポーネント一覧、状態遷移、レスポンシブ仕様まで落とし込む

# 3. 設計書からコードを自動生成（実装フェーズを委任）
/implement
# → 仕様に基づきソースコードを生成

# 4. テストを実行して結果を確認
/test

# 5. 差分を検証したうえでコミット
/commit

# 6. クリーンなcommit/worktreeであることを確認してからデプロイ
/deploy
```

このパイプラインの肝は、各ステップが「独立したコンテキストを持つサブエージェント」として動く点にある。監査を行うエージェントは実装の詳細を知らないし、実装するエージェントは経営判断の文脈を持たない。それぞれが必要な情報だけを受け取って動くことで、コンテキストの汚染を防いでいる。

特に`/deploy`の前段には検証専用のサブエージェントを置いている。未コミットの作業内容が紛れ込んでいないか、差分が意図通りかを独立してチェックしてから初めてデプロイを許可する構成だ。これは実際に「未コミットのWIPを含んだままデプロイしてしまう」という事故を経験したあとに追加したガードレールで、AIに実行権限を渡すなら検証ステップを別エージェントに切り出すべき、というのが得られた教訓だった。

## 記憶システムの設計：なぜMarkdown+YAMLフロントマターなのか

OpenClaw側の「記憶」は、単なるログの蓄積ではなく、種類ごとに構造化されている。筆者が採用しているのは以下の4分類だ。

- **user**: ユーザーの役割・専門性・知識レベル
- **feedback**: 過去の指摘・修正・「これは良かった」という確認
- **project**: 進行中の意思決定・締切・背景にある制約
- **reference**: 外部システム（Linear、Slack、Grafanaなど）への参照先

各メモリはこういう形式のファイルとして保存する。

```markdown
---
name: deploy-safety-rule
description: 未コミットWIP混入によるデプロイ事故の再発防止ルール
metadata:
  type: feedback
---

デプロイ前に必ず git status でクリーンな状態を確認する。
**Why:** 過去に未コミットの実験コードを含んだままデプロイした事故があった。
**How to apply:** /deploy 実行前に deploy-verifier 相当の検証エージェントを必ず通す。
```

そして`MEMORY.md`という1ファイルにインデックスとして集約し、1行150文字以内の要約だけを常時コンテキストに載せる設計にしている。これにより、記憶が増えてもコンテキストウィンドウを圧迫せず、必要なときだけ該当ファイルを深掘りできる。

この「インデックスは軽く、本体は必要時にロード」という設計は、思考の粒度が違うOpenClawとClaude Codeを繋ぐうえで地味に効いている。経営判断のペルソナは要約だけ見て動き、実行層は必要なファイルだけをReadする、という非対称なアクセスパターンが成立するからだ。

## つまずいたポイント：無人運用は思ったより怖い

正直に書くと、この構成を無人のcronで動かし始めた当初は何度かヒヤリとした。

一番大きな教訓は「AIに実行権限を渡すコストは、思っている以上に非対称」ということだ。文章生成や分析だけなら失敗しても書き直せばいいが、デプロイやSNS投稿、決済関連の操作は取り返しがつかない。そこで筆者の環境では以下のような安全ルールをOpenClaw側の常時コンテキストに固定している。

- 有料API呼び出しは決まった経路（Claude CLI）以外は禁止し、従量課金APIの新規呼び出しは人間承認を必須にする
- SNS投稿は下書きまでを自動化し、公開は必ず人間承認を挟む
- 同一アカウントへの連続投稿には最低間隔を強制する（プラットフォームのスパム判定を避けるため）
- デプロイは必ずクリーンなcommit/worktreeから行い、差分検証を別エージェントで独立して通す

これらは全て「一度失敗してから追加したルール」であり、最初から完璧な安全設計を用意できていたわけではない。逆張り的な結論になるが、AIオーケストレーションを無人で回す場合、最初の設計で完璧を目指すより「小さく失敗して即座にルール化する」サイクルを回すほうが実用上は速い。OpenClawの`feedback`メモリはまさにこのサイクルを支えるための仕組みとして機能している。

## AI活用スキルとキャリアの掛け算：SES・フリーランスエンジニアの視点から

少し話がそれるが、この連携パターンを構築する過程で気づいたことがある。SESや客先常駐でキャリアを積んできたエンジニアほど、こうしたAIオーケストレーションの設計スキルは今後の市場価値に直結しやすい、という点だ。

SES 1年目で転職やキャリアの方向性に迷うエンジニアは多いが、単一の言語・フレームワークの習熟度だけで年収やSES単価相場が決まる時代は終わりつつある。むしろ「複数のAIエージェントに役割を分担させて、監査から実装、デプロイまでの一連の開発フローを設計できるか」という、システム設計に近いスキルが評価される場面が増えている。

フリーランスとしてSESを離れる選択をする場合も、こうした自動化パイプラインを自分の武器として持っているかどうかで、案件単価の交渉力は変わってくる。SES単価相場は案件やスキルセットによって幅が大きいが、AIツールを使いこなして開発スピードや監査の精度を上げられるエンジニアは、単純な工数ベースの評価から抜け出しやすい。SESという働き方自体を否定するわけではなく、そこで得られる多様な現場経験と、AIオーケストレーションのスキルを掛け算できるかどうかが、今後の年収レンジを左右する分岐点になっていくはずだ。

## まとめ

OpenClawとClaude Codeの連携は、突き詰めると「判断は文脈を保持したエージェントに、実行は使い捨てのサブエージェントに」という役割分担の設計に尽きる。

- 経営判断のペルソナ（CEO/CFO/CTO/COO/CMO）が優先順位を判断し、指示を出す
- Claude Code側の独立したサブエージェントが監査・設計・実装・検証・デプロイを分担して実行する
- 記憶はtype別に構造化し、インデックスは軽く、本体は必要時にロードする設計にする
- 実行権限を持つ操作（デプロイ、投稿、決済）には必ず検証ステップと人間承認を挟む

完璧な設計を最初から作ろうとせず、失敗をfeedbackメモリとしてルール化していくサイクルこそが、無人運用を安定させる一番の近道だった。これから自分の開発フローにAIオーケストレーションを組み込みたいエンジニアには、まず「思考」と「実行」を分離するところから始めることをおすすめしたい。

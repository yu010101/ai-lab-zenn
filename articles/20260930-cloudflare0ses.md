## 今、なぜ「軽量なページ内検索」が注目されているのか

SaaS型の全文検索(Algolia、Elasticsearchのマネージドサービスなど)は便利な反面、月額課金がボトルネックになりがちです。個人開発やスモビジのオウンドメディアでは、月数千〜数万円の検索SaaS費用が地味に利益を圧迫します。

一方で最近のトレンドは「ビルド時に検索インデックスを静的ファイルとして生成し、クライアント側(ブラウザ)で完結させる」方式です。サーバー側で検索クエリを処理しないため、Cloudflare Pagesのような静的ホスティングの無料枠だけで高品質な検索体験を作れます。Zennのトレンドに上がっていた「Jev」もこの潮流に乗ったツールとして名前が挙がっており、AI活用と並んで「エンジニアが自分のメディア運用コストを削る」ニーズが強くなっていることの表れだと捉えています。

本記事では、この思想を体現する代表的なOSSである **Pagefind** を使い、実際にCloudflare Pages上で動かすところまで検証します。Pagefindは静的サイト向けの検索インデックスをビルド時に生成し、WebAssemblyでブラウザ内検索を実現するオープンソースツールで、サーバーコストがかからない設計になっています。

## Cloudflareで「ほぼ0円」の高品質ページ内検索を構築する

### アーキテクチャ

```
[静的サイトのビルド] → [Pagefindでインデックス生成] → [Cloudflare Pagesにデプロイ]
                                                              ↓
                                            ブラウザがWASMで検索インデックスを読み込み
                                            → サーバー通信なしで検索結果を返す
```

サーバーサイドの検索APIが存在しないため、リクエスト課金もDBのスケーリング費用も発生しません。かかるのはCloudflare Pagesの無料枠(静的ホスティング)とドメイン代くらいです。

### 手順1: ビルド時にインデックスを生成する

静的サイトジェネレータ(Astro、Next.jsのexportモード、Hugoなど何でも構いません)でHTMLを出力した後、Pagefindでインデックス化します。

```bash
# インストール
npm install -D pagefind

# ビルド済みの静的ファイル(distディレクトリ)に対してインデックスを生成
npx pagefind --site dist
```

実行するとdist配下に`pagefind`ディレクトリが作成され、検索用のインデックスファイル一式(JSONとWASM)が出力されます。

### 手順2: package.jsonにビルドフックを組み込む

```json
{
  "scripts": {
    "build": "astro build && npx pagefind --site dist"
  }
}
```

こうしておくとCloudflare Pagesのビルドコマンドを`npm run build`にするだけで、デプロイのたびに検索インデックスが自動更新されます。

### 手順3: Cloudflare Pagesにデプロイする

```bash
# wranglerでpagesプロジェクトを作成(初回のみ)
npx wrangler pages project create my-search-site

# デプロイ
npx wrangler pages deploy dist --project-name=my-search-site
```

### 手順4: 検索UIを埋め込む

```html
<div id="search"></div>
<script src="/pagefind/pagefind-ui.js"></script>
<script>
  new PagefindUI({ element: "#search", showSubResults: true });
</script>
```

これだけでキーワード入力に応じたインクリメンタルサーチが動きます。実測ではインデックスサイズは記事数百本規模でも数MB程度に収まり、初回ロード後はほぼ体感遅延なしで検索結果が返ってきました。

### コスト試算(概算)

| 項目 | SaaS型検索(例: 有料プラン) | 静的インデックス型(Pagefind+Cloudflare Pages) |
|---|---|---|
| 月額固定費 | 数千円〜 | 0円(無料枠内) |
| リクエスト課金 | 検索回数に応じて発生する場合あり | なし(クライアント完結) |
| インフラ管理 | ダッシュボード管理が必要 | ビルドパイプラインに統合するだけ |
| オフライン動作 | 不可 | インデックス読み込み後は可能 |

記事数が少ない個人ブログはもちろん、noteやZennに書けない自社ドキュメント・社内Wikiのような「検索SaaSにお金をかけたくないが検索体験は落としたくない」場面で特に効果が出やすい構成です。

## AI駆動塾的な視点: この仕組みを「商品」にする考え方

技術検証で終わらせず、スモールビジネスに繋げるならどう動くか。実務でよくあるのは次のような展開です。

- **テンプレート化して販売する**: Astro/Next.js + Pagefind + Cloudflare Pagesの構成をボイラープレート化し、booth等で有料配布する
- **導入代行を提供する**: 検索SaaSの月額費用に困っている中小企業のオウンドメディア担当者向けに、初期構築を数万円のスポット案件として請け負う
- **ノウハウを継続コンテンツにする**: 本記事のような「実際に手を動かして検証したログ」自体をnoteメンバーシップなどのストック型コンテンツにする

AIツール(Claude CodeやOpenClawなど)を使えば、この手のボイラープレート整備や検証記事の下書き生成自体をかなり高速化できます。実際に私が使っている流れは、Claude Codeにwrangler.tomlやビルドスクリプトの雛形を生成させ、人間が最終確認とデプロイ判断だけを行う、という役割分担です。AIに任せるのは「手を動かす部分」、人間が握るのは「何を作るか・公開するかの意思決定」という線引きが、事故を防ぐ上でも重要だと感じています。

## 【保存版】ページ内検索導入チェックリスト

後で見返せるように、導入判断のチェックリストをまとめておきます。ブックマークや保存推奨です。

- [ ] サイトの記事数・データ量を把握したか(数百〜数千件規模ならPagefind型が有力)
- [ ] 検索SaaSの月額費用と、静的インデックス型の構築工数を比較したか
- [ ] ビルドパイプラインに検索インデックス生成ステップを追加できる構成か
- [ ] 更新頻度に対して、ビルド〜デプロイの所要時間が許容範囲か
- [ ] 検索対象コンテンツに機密情報が含まれないか(クライアントサイド完結=全データがブラウザに配信される前提)
- [ ] Cloudflare Pagesの無料枠の範囲(帯域・ビルド回数)を確認したか
- [ ] 検索UIのカスタマイズ(日本語トークナイズの精度など)を事前に検証したか

特に最後の「機密情報を含まないか」は見落としがちです。クライアントサイド検索はインデックス自体がブラウザに配信される設計なので、非公開情報を含むページを誤って検索対象に含めないよう、ビルド時の除外設定(exclude属性など)を必ず確認してください。

## SESエンジニアが知っておきたい、フリーランス転向と年収の考え方

ここからは少し毛色を変えて、SES企業に所属するエンジニアがフリーランスへの転向を考えるときの実務的な論点を整理します。

### SES フリーランス 転向でよくある失敗と回避策

- **単価交渉の材料を持たずに転向する**: SES時代の給与明細だけを基準に案件単価を決めてしまい、市場相場より低い単価で契約してしまうケース。フリーランス協会が毎年公表している「フリーランス白書」など一次情報で自分の技術領域の相場感を確認してから交渉するのが先です。
- **契約書の支払いサイトを確認せずに契約する**: 検収から入金までの期間(支払いサイト)を確認しないまま常駐を始め、資金繰りが厳しくなるケース。契約前に支払いサイトと検収条件を必ず書面で確認する。
- **確定申告・社会保険の切り替えを後回しにする**: 会社員時代は自動だった手続きが自分事になるため、開業届や青色申告の準備を転向直前に慌てて行うケースが多く、転向の数ヶ月前から準備しておくと安心です。

### フリーランス 案件 探し方の基本

- **エージェント経由**: SES出身者にとって最も移行しやすいのがITフリーランス向けエージェントの活用です。SES時代の案件経験(業務内容・使用技術)をそのまま職務経歴として棚卸しし、複数エージェントに同時登録して単価を比較するのが基本です。
- **直接契約・紹介**: SES時代に関わったクライアントや協力会社との人脈から直接契約に繋げるルートもあります。ただし現職との契約(競業避止義務など)に抵触しないか事前確認が必須です。
- **技術発信経由**: 本記事のようにQiitaやZennで技術検証を発信し続けることが、結果として直接オファーや紹介につながることもあります。AIタグやJevタグのように「今伸びているトピック」に早めに触れておくことは、発信の見つかりやすさという意味でも意味があります。

年収は経験年数・技術領域・単価交渉力で大きく変わるため、断定的な数字を出すよりも、まず自分の職務経歴を一次情報(フリーランス白書、エージェントの公開単価データなど)と突き合わせて相場感を掴むことをおすすめします。

## まとめ

- Cloudflare Pages + Pagefindのような「ビルド時にインデックス生成、クライアントサイドで検索完結」の構成は、検索SaaSの月額費用をほぼゼロに近づけられる
- この技術検証自体が、テンプレート販売・導入代行・コンテンツ化というスモビジのネタになる
- SESからフリーランスへの転向は、単価交渉の材料・契約条件の確認・案件探しのルート整理を事前にやるかどうかで結果が大きく変わる

技術のキャッチアップと、それをどう収益化するかの視点を両方持つことが、これからのエンジニアの働き方の選択肢を広げてくれると感じています。

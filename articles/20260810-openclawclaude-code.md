## はじめに：なぜ「思考」と「実行」を分離するのか

2026年現在、AIエージェントを開発ワークフローに組み込むエンジニアが増えていますが、多くの人がぶつかる壁は「1つのAIに全部やらせようとして破綻する」というパターンです。要件整理・意思決定・記憶の保持と、実際のコーディング・テスト・デプロイを同じコンテキストでやらせると、会話が長くなるほど精度が落ち、途中で文脈を見失います。

筆者が実務で採用しているのが、**OpenClaw（思考・記憶・指示を担当するAI経営OS）**と**Claude Code（開発・実行を担当するコーディングエージェント）**を役割分担させる構成です。この記事では、実際に使っているコマンドと構成をベースに、具体的な連携パターンを紹介します。SES（システムエンジニアリングサービス）で働くエンジニアが、こうしたAI活用スキルを単価・年収にどう結びつけていけるかにも最後に触れます。

## OpenClawとClaude Codeの役割分担

両者を同じ土俵で比較すると、得意領域の違いがはっきりします。

| 項目 | OpenClaw | Claude Code |
|---|---|---|
| 主な役割 | 意思決定・優先度判断・記憶の永続化 | コード実装・テスト実行・デプロイ |
| 記憶の持ち方 | YAML/Markdownベースの構造化メモリ（inbox/today/archive） | セッション単位のコンテキスト＋プロジェクトファイル |
| 得意なタスク | 経営判断、進捗の横断把握、部署間の情報統合 | ファイル編集、テスト、git操作、CI連携 |
| インターフェース | スラッシュコマンド（/ceo, /cfo, /coo など） | 自然言語プロンプト＋ツール呼び出し |

ポイントは、OpenClaw側に「何を・なぜやるか」を蓄積させ、Claude Code側は「どうやるか」に集中させることです。これにより、Claude Codeのコンテキストウィンドウを実装作業だけに使えるため、長時間のセッションでも精度が落ちにくくなります。

## ユースケース1：経営ダッシュボードから開発タスクへの落とし込み

複数プロダクトを運営している場合、まずOpenClaw側で状況を俯瞰します。

```bash
# 経営ダッシュボード全体を確認
/ceo dash

# CTOエージェントでプロダクトのヘルスチェック
/cto health

# 技術的な優先度を提案させる
/cto priority
```

`/cto priority` は各プロダクトの技術負債・バグ報告・稼働状況を横断的に見て「今週着手すべき技術タスク」を提示してくれます。ここで得られた優先度リストを、そのままClaude Codeに渡します。

```bash
claude "OpenClawのCTOエージェントが優先度1位と判定したタスクを実装してほしい。
対象: [プロダクトA] のAPIレスポンス遅延の原因調査と修正。
背景: 直近のヘルスチェックでレイテンシ悪化が検出されている。"
```

Claude Code側では、原因調査→修正→テスト→PR作成までを一気通貫で行わせます。実装が終わったら、結果をOpenClaw側に戻して記憶を更新します。

```bash
# 対応結果をOpenClawの秘書エージェントに記録
/cc-secretary list
```

cc-secretaryはinbox/today/archiveのYAMLを操作する秘書エージェントで、「何を判断し、何を実行し、結果どうだったか」を構造化して残します。この記録が次回の`/cto priority`実行時に参照され、同じ議論を繰り返さずに済むのが大きな利点です。

## ユースケース2：財務・営業データと開発判断の統合

もう一つよく使うのが、財務状況を踏まえた開発優先度の調整です。

```bash
# 未決済・支払い状況を確認
/cfo 未決済

# 営業パイプラインとクライアント状況を確認
/coo clients
```

例えば「特定クライアント向け機能の優先度を上げるべきか」を判断する際、COOエージェントが持つ営業パイプラインの情報とCFOエージェントが持つ財務データを突き合わせることで、単なる「バグの重大度」だけでなく「事業インパクト」を加味した優先順位付けができます。この判断結果をClaude Codeへのプロンプトに含めることで、実装の優先順位付けにビジネス文脈を持ち込めます。

## ユースケース3：cronによる定期実行とメモリの継続性

OpenClaw側のエージェントは、cronで定期実行させることで「毎朝プロダクトの状態を確認し、異常があればタスク化する」といった運用が可能です。ここで重要なのは、無人実行時の安全策です。実務では以下のようなルールを徹底しています。

- 有料API呼び出しは決められたCLI経由に限定し、従量課金APIの新規呼び出しを無人実行では許可しない
- SNSなど外部への公開アクションは自動化せず、下書き生成までに留めて人間承認を挟む
- 常駐が必要なプロセスはlaunchdではなくPM2で管理し、認証まわりの死活監視を最優先で行う

こうしたガードレールをOpenClaw側の運用ルールとして明文化しておくことで、Claude Codeに実装を任せる際も「無人実行で何をしてはいけないか」がぶれません。

## 実際にやってみて感じたこと

運用を始めてまだ日が浅いため、定量的な効果検証はこれからですが、質的には次のような変化を感じています。

- **コンテキストスイッチが減った**：意思決定はOpenClaw、実装はClaude Codeと分けたことで、「何をするか悩みながらコードを書く」状態が減った
- **判断の再利用性が上がった**：cc-secretaryに記録した過去の判断を、次のタスク優先度付けで参照できるため、同じ議論を繰り返さない
- **実装の手戻りが減った**：ビジネス文脈（財務・営業状況）を踏まえたプロンプトをClaude Codeに渡すことで、「技術的には正しいが優先度がずれた実装」が減った

ここで強調しておきたいのは、これらはあくまで運用初期の体感であり、まだ「安定稼働している」と言い切れる段階ではないということです。1〜2週間、数週間という単位で実績を積んでから、改めて定量的な振り返りをする予定です。

## つまずきやすいポイント

実際に構築・運用する中で気をつけているポイントをまとめます。

1. **記憶の粒度設計**：OpenClaw側のメモリに何でも書き込むと肥大化して逆に検索性が落ちます。判断理由（Why）と適用条件（How to apply）をセットで残す設計が重要です。
2. **エージェント間の責任境界**：「思考担当のOpenClawが実装の細部にまで口出しする」「実行担当のClaude Codeが勝手に優先度を変える」といった越権が起きないよう、プロンプトで役割を明示します。
3. **無人実行の暴走防止**：cronで定期実行するエージェントには、必ず実行結果をログ化し、異常検知の仕組みを別途用意しておく必要があります。

## SESエンジニアの単価・年収への影響

ここまで紹介した「思考と実行を分離するAI活用」は、SESエンジニアのキャリアや単価にも無関係ではありません。SES業界では従来、稼働時間や保有スキルセットが単価・年収の主な評価軸でしたが、AIエージェントを使いこなして開発生産性を上げられる人材への需要は今後も高まっていくと考えられます。

SES 単価 相場を調べる際は、単純な言語・フレームワークの経験年数だけでなく、「AIツールを使った開発フローをどれだけ構築・運用できるか」という観点も評価材料に加わりつつあります。特にSES 1年目 転職を考えているエンジニアであれば、Claude CodeのようなAIコーディングエージェントの実務活用経験は、案件選定や単価交渉での差別化ポイントになり得ます。

もちろん、これは筆者の実務での実感であり、具体的な単価上昇幅や年収の統計データについては、各種SES企業やエージェントが公表する最新の市場調査を確認することをおすすめします。抽象的な「AIで稼げる」という話ではなく、実際にどのツールをどう組み合わせ、どんな業務プロセスを構築できるかという具体性が、単価・年収交渉の説得材料になります。

## まとめ

OpenClawとClaude Codeを役割分担させる構成は、「意思決定と記憶」を担うレイヤーと「実装と実行」を担うレイヤーを分離することで、それぞれのAIエージェントの強みを最大化するアプローチです。

- OpenClaw：経営判断・優先度付け・記憶の永続化（/ceo, /cfo, /coo, /cmo, /cto, /cc-secretary など）
- Claude Code：ファイル編集・テスト・git操作・デプロイなどの実装作業

この分離により、Claude Code側は実装に集中でき、OpenClaw側は長期的な文脈を保持し続けられます。まだ運用実績は浅いものの、今後継続的に定量データを積み上げ、SESエンジニアとしての単価・年収戦略も含めて振り返っていく予定です。

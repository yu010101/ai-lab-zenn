## SESエンジニアなら知っておきたい、Claude Codeの実務活用法

「AIコーディングツールって結局バズワードでは?」と思っている人ほど、実際に手を動かして試してほしい。今日は普段の開発でClaude Codeをどう使っているか、実際に動くコマンドと設定を交えて紹介する。SESでアサインされた現場でも、個人の学習環境でも、そのまま使える内容にしたつもりだ。

### この記事の対象読者

- SESエンジニアとして常駐先で開発をしているが、自分のスキルを客観的に把握できていない人
- SESからフリーランスへの独立を検討しているが、何から手をつければいいか分からない人
- SES 1年目で「このままでいいのか」と転職を意識し始めた人

## 1. Claude Codeのセットアップは3分で終わる

まずインストールと初期設定から。

```bash
npm install -g @anthropic-ai/claude-code
cd ~/projects/your-repo
claude
```

起動したら `/init` を実行すると、プロジェクトを読み込んでCLAUDE.mdという設定ファイルを自動生成してくれる。これはClaude Codeがそのプロジェクトの文脈(技術スタック、ディレクトリ構成、コーディング規約など)を毎回のセッションで覚えておくためのメモリファイルだ。

```
/init
```

生成されたCLAUDE.mdは手で編集できる。例えば常駐先の案件でよくある「このリポジトリはLintルールが厳しい」「テストはVitestを使う」といった暗黙知を書いておくと、次回以降のセッションで毎回説明し直す手間が消える。

```markdown
# CLAUDE.md
## コーディング規約
- コンポーネントは関数コンポーネント + TypeScriptのみ
- テストはVitest、E2EはPlaywright
- コミットメッセージはConventional Commits形式
```

## 2. 自分のコミット履歴をデータ分析してキャリアの棚卸しをする

SESエンジニアが一番損をしているのは「自分が何をやってきたか」を定量的に説明できないことだと思う。単価交渉や転職面談で「頑張りました」しか言えないと、年収交渉の材料にならない。

そこでやってみたのが、自分のgitコミット履歴をClaude Codeに分析させてスキルの棚卸しをする方法だ。

```bash
git log --author="自分の名前" --since="1 year ago" \
  --pretty=format:"%ad %s" --date=short > my_commits.txt
```

このテキストファイルをClaude Codeに読ませて、こう聞く。

```
my_commits.txtを読んで、直近1年でどの技術領域(フロントエンド/バックエンド/インフラ/データ分析など)にどれくらいの比重で取り組んでいたか集計して。案件の単価交渉に使える形でサマリーして。
```

Claude Codeはファイルを読み込み、コミットメッセージのパターンから技術領域を分類し、Markdownの表にまとめてくれる。これを職務経歴書や、次の案件面談での「自分の強み」の根拠として使っている。感覚ではなく実際のコミット数・変更行数というデータに基づいているので、単価交渉の場でも説得力が違う。

`git log --stat` を使えば変更行数まで拾えるので、より精緻なデータ分析ができる。

```bash
git log --author="自分の名前" --since="6 months ago" --stat \
  --pretty=format:"### %ad %s" --date=short > my_activity.txt
```

## 3. カスタムスラッシュコマンドで日報・週報を自動化する

SESの現場では日報や週報の提出を求められることが多い。これも手動で書くと地味に時間を取られる。Claude Codeはプロジェクト固有のスラッシュコマンドを`.claude/commands/`配下にMarkdownファイルとして定義できる。

```bash
mkdir -p .claude/commands
```

```markdown
<!-- .claude/commands/weekly-report.md -->
今日のgit logとGitHub Issuesのクローズ履歴を確認し、
今週やったことを箇条書きでまとめて。専門用語は使わず、
非エンジニアの担当者にも伝わる表現にして。
```

これで `/weekly-report` と打つだけで週報のたたき台が生成される。もちろん出した内容は必ず自分で確認・修正してから提出しているが、ゼロから書くのに比べて圧倒的に時間が短縮できる。

## 4. Plan Modeで「勝手に実装される」事故を防ぐ

SESの現場では複数人のリポジトリを触ることが多く、AIに勝手にコードを書き換えられると事故につながる。Claude CodeにはPlan Modeがあり、`Shift+Tab`で切り替えると、実際にファイルを編集する前に計画だけを提示してくれる。

自分は複雑なタスク(3ステップ以上、あるいは設計判断が絡むもの)は必ずPlan Modeで一度計画を確認してからGOを出すようにしている。これをやらずに「とりあえず直しといて」で走らせると、意図しない箇所まで手が入ることがある。地味だが、常駐先の信頼を失わないための最低限の作法だと思っている。

## 5. サブエージェントで大きめの調査タスクを切り出す

Claude Codeにはサブエージェント機能があり、`.claude/agents/`にMarkdownでエージェント定義を書いておくと、メインの会話コンテキストを汚さずに調査や並列処理を任せられる。

```markdown
<!-- .claude/agents/researcher.md -->
---
name: researcher
description: コードベース内の特定パターンを横断的に調査する
tools: Read, Grep, Glob
---
あなたはコードベースの調査専門エージェントです。
```

例えば「このリポジトリ全体でどのAPIエンドポイントが認証チェックを実装していないか調べて」といった横断調査を投げると、サブエージェントが個別に探索して結果だけを返してくれる。メインのセッションのコンテキストウィンドウを消費しないので、長時間の作業でも会話が破綻しにくい。

## 6. hooksで「うっかりミス」を機械的に防ぐ

`.claude/settings.json`にhooksを設定すると、ファイル編集後に自動でLintやフォーマッタを走らせられる。

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "npx eslint --fix $CLAUDE_FILE_PATH" }
        ]
      }
    ]
  }
}
```

AIが編集した直後に機械的にLintがかかるので、「AIが書いたコードのフォーマット崩れ」を人力でチェックする手間が減る。SESの現場は複数のリポジトリ規約が混在しやすいので、この自動化は地味に効く。

## 7. MCPで外部データと連携してタスク消化を分析する

MCP(Model Context Protocol)を使うと、GitHub Issuesなど外部サービスのデータをClaude Codeから直接参照できる。

```bash
claude mcp add github -- npx -y @modelcontextprotocol/server-github
```

接続後は「直近1ヶ月でクローズしたIssueの件数と、担当したラベル(bug/feature/refactor)の内訳を集計して」といった指示で、自分のタスク消化傾向をデータ化できる。これも職務経歴書やフリーランス転向時のポートフォリオ説明に使える材料になる。

## 8. SESエンジニアがデータ分析スキルを武器にする理由

ここからは少し本業寄りの話。SESという契約形態は「常駐先の指示で作業する」性質上、自分の成果が見えにくくなりがちだ。だからこそ、上で紹介したような「自分の作業をデータで可視化する」習慣そのものが、他のSESエンジニアとの差別化になると考えている。

### SES 1年目でも今日からできること

SES 1年目で「この案件、自分は成長できているのか」と不安になるのはよくあることだ。焦って転職活動を始める前に、まず自分のコミット履歴やタスク消化数を定期的に記録し、半年〜1年単位で振り返る習慣をつけることをおすすめしたい。データがあれば、上長との評価面談でも「感覚」ではなく「事実」で会話ができる。SES 1年目の転職判断は、勢いではなくこうした記録を根拠にするほうが後悔が少ない。

### SESからフリーランスへのロードマップ

SESからフリーランスへの独立を考えるなら、いきなり契約形態を変えるのではなく、まず社内で技術的な裁量が大きい案件にアサインしてもらえるよう動き、実装だけでなく設計・要件定義まで経験を広げておくのが定石だ。フリーランスの案件では「言われたことをやる」だけでなく「何を作るべきかを提案する」力が問われる場面が多いため、SES期間中にその経験を積めるかどうかが独立後の単価に直結する。

| 比較観点 | SES(客先常駐) | フリーランス |
|---|---|---|
| 案件の決め方 | 会社が調整・アサイン | 自分で契約交渉 |
| 収入の安定性 | 給与制で安定しやすい | 契約が切れると収入が途切れるリスク |
| 裁量の範囲 | 現場の指示に従う比重が高い | 提案・設計から関わりやすい | 
| 事務・営業負担 | 会社が代行 | 契約書・請求・確定申告を自分で対応 |

### 失敗談・リスクとして知っておくべきこと

SESからフリーランスへの独立でよく聞くトラブルは、契約書の業務範囲が曖昧なまま常駐を続けてしまい、多重下請け構造の中で実質的な指揮命令系統が不透明になるケースだ。これは労働者派遣法・偽装請負の観点で問題になりうる領域なので、独立前に自分の契約形態と実際の働き方が一致しているかを確認しておくべきだと思う。不安がある場合は、契約書の内容を専門家(社労士や弁護士)に確認してから動くのが安全だ。「単価が上がるから」という理由だけで契約形態を変えると、後からトラブルの矢面に立つのは自分自身になる。

## まとめ

Claude Codeは「コードを書いてくれるツール」以上に、自分の開発活動そのものをデータとして扱えるようにしてくれるツールだと感じている。SESという立場だからこそ、自分の成果を定量的に説明できる材料を日常的に積み上げておくことが、年収交渉やフリーランスへの移行を考えるうえでの一番の武器になる。

まずは `git log` を自分のコミットに絞って出力し、Claude Codeに読ませてみることから始めてみてほしい。

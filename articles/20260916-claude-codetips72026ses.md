## Tips 1: CLAUDE.mdはプロジェクト用とグローバル用を分けて育てる

Claude Codeを使い始めた頃は、プロジェクト直下の`CLAUDE.md`に全部書いていた。しばらく運用してみて分かったのは、「その日一回きりの指示」と「今後もずっと守ってほしいルール」を同じファイルに混ぜると、すぐにファイルが肥大化して読み込みコストが増えるということだ。

今の運用は以下のように分けている。

```
~/.claude/CLAUDE.md          # 全プロジェクト共通のワークフロー方針
<project>/CLAUDE.md          # そのリポジトリ固有の規約・アーキテクチャ
<project>/tasks/lessons.md   # ユーザーから指摘を受けた失敗パターンの蓄積
```

CLAUDE.mdの中身は「何をするか」ではなく「どう判断するか」を書くのがコツだ。例えばこんな感じ。

```markdown
## Core Principles
- Simplicity First: 変更は必要最小限に留める
- No Laziness: 場当たり対応ではなく根本原因を直す
- Minimal Impact: 影響範囲を広げない
```

自分がした修正を毎回`tasks/lessons.md`に追記しておくと、次のセッションで同じ指摘を二度されなくなる。これはユーザーから訂正を受けたときに使う自己改善ループとして地味に効果がある。

## Tips 2: 3ステップ以上のタスクは必ずPlan Modeを通す

「とりあえずコード書いて」で進めると、途中で方針がズレていることに後から気づいて手戻りが発生する。Claude CodeにはPlan Modeがあり、実装前に計画だけを立てさせて、承認してから着手させることができる。

体感ルールとして自分は「3ステップ以上、または設計判断を伴うタスクは必ずPlan Modeを通す」と決めている。CLAUDE.mdにもそのまま書いておくと、Claude Code側が自律的にPlan Modeへの移行を提案してくれるようになる。

```markdown
### Plan Mode Default
- 非自明なタスク（3ステップ以上 or アーキテクチャ判断）は必ずPlan Modeに入る
- 想定外の事態が起きたら、押し切らずに即座に再計画する
```

計画は`tasks/todo.md`にチェックリスト形式で書き出させて、実装が進むたびにチェックを入れさせる。これをやるだけで「今どこまで終わっているか」が一目で分かるようになり、長時間セッションでのコンテキスト圧縮後も迷子にならない。

## Tips 3: サブエージェントは「調査」と「実装」を分離するために使う

メインのセッションで自分でgrepしまくると、探索の途中結果がコンテキストを圧迫して、肝心の実装フェーズで使えるコンテキストが減ってしまう。これを避けるために、探索系のタスクは読み取り専用のサブエージェントに投げるようにしている。

- ファイルパターン検索や「このシンボルがどこで定義されているか」系のクエリ → 読み取り専用の探索エージェントに投げる
- 独立して並列実行できる複数の調査（例：3つのライブラリの比較調査）→ 並列でサブエージェントを起動する
- コードレビューやアーキテクチャ監査 → 専用のレビューエージェントに投げる

`.claude/agents/`配下にカスタムエージェントを定義しておくと便利だ。フロントマターでツール権限を絞れるので、探索用エージェントにはEditやWriteの権限を渡さない、という設計にできる。

```markdown
---
name: explore-readonly
description: 読み取り専用でコードベースを探索する
tools: Read, Grep, Bash
---

コードベースの構造調査に専念する。ファイルの編集は一切行わない。
```

「調査は投げる、判断は自分（メインセッション）でする」という役割分担を徹底すると、メインのコンテキストウィンドウが長持ちする。

## Tips 4: Hooksで「うっかり事故」を仕組みで防ぐ

どれだけCLAUDE.mdに書いても、AIも人間と同じで「うっかり」は起きる。うっかりを防ぐ最後の砦がHooksだ。`settings.json`に設定を書いておくと、特定のツール呼び出しの前後にシェルコマンドを挟める。

自分が実際に使っているのは、破壊的なgitコマンドを実行する前に警告を出す設定だ。

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "scripts/check-destructive-git.sh"
          }
        ]
      }
    ]
  }
}
```

`check-destructive-git.sh`の中身は単純で、標準入力で渡ってくるコマンド文字列に`git push --force`や`git reset --hard`が含まれていたら非ゼロで終了してブロックする、というものだ。CLAUDE.mdの「お願いベースのルール」と違い、Hooksは仕組みとして強制できるのが強い。無人実行（cronでの自動化タスクなど）をする場合は、このHooksによる安全弁がないと事故る前提で考えたほうがいい。

## Tips 5: カスタムスラッシュコマンドで定型作業をショートカット化する

毎回同じ手順を口頭で説明するのは無駄なので、頻出パターンは`.claude/commands/`にMarkdownファイルとして切り出している。

```markdown
---
description: 変更差分に対してコードレビューを実行する
---

現在のdiffを対象に、正確性のバグと重複コードの観点でレビューしてください。
重大度が高い順に列挙し、確信度が低いものは「要確認」と明記してください。
```

これを`/review-diff`のように呼び出すだけで、毎回プロンプトを打ち直す手間がなくなる。加えて`/compact`でコンテキストを圧縮したり、`/clear`でセッションをリセットしたりといった標準コマンドも、長時間の実装セッションでは意識的に使うようにしている。特に大きめのリファクタリングをしたあとは、無関係な過去のやり取りがコンテキストに残ったまま次のタスクに入らないよう、区切りのタイミングで`/clear`するのがクセになった。

## Tips 6: MCPで外部ツールを「会話の中」に持ち込む

Model Context Protocol（MCP）を使うと、Claude Code自体は変えずに外部サービスとの連携を追加できる。自分の環境では、GitHub操作は素のgitコマンドで完結するのでMCPを使わず、代わりに社内ドキュメント検索や分析基盤へのアクセスなど「CLIだけでは完結しない外部データ」を扱う場面でMCPサーバーを繋いでいる。

```bash
claude mcp add my-internal-search -- npx -y @internal/mcp-search-server
```

MCP経由のツールはデフォルトでは読み込まれず、必要になったタイミングで遅延ロードされる設計になっているため、繋ぐサーバーの数を増やしてもベースのコンテキスト消費が際限なく増えるわけではない。ただし認証が必要なMCPサーバー（例えばブラウザ認証が必要なもの）は、無人実行環境（cronなど）だと認証切れで死ぬことがあるので、無人運用に組み込む場合は認証方式を必ず確認したほうがいい。

## Tips 7: コンテキストとコストは「投げる前」に設計する

Claude Codeは会話が長くなると自動でサマリー圧縮が入るが、それに頼り切ると「圧縮された結果、さっき決めた大事な制約が消えた」という事故が起きる。自分がやっているのは以下の3つだ。

1. 大事な決定事項は会話に流さず、都度`tasks/todo.md`やCLAUDE.mdに書き出す（会話がどれだけ圧縮されてもファイルは消えない）
2. 調査系タスクはサブエージェントに切り出し、メインセッションには結論だけを戻す
3. 有料APIを叩く自動化は必ずClaude CLI経由に統一し、Anthropic APIを従量課金で直接叩く経路を新規に増やさない

特に3つ目は、無人のcronジョブなどを組む際に地味に効いてくる。課金経路が分散すると、どこでコストが発生しているのか追いにくくなるし、想定外の高頻度呼び出しに気づくのも遅れる。

## 他のAIコーディングツールとの使い分け

「Claude CodeとCursor、GitHub Copilot、Codexはどう使い分けるか」という質問をよく見かける。厳密なベンチマーク比較は数字がすぐ古くなるのでこの記事ではしないが、実務上の使い分けの軸としては以下のように整理している。

| 観点 | 向いている場面 |
|---|---|
| 長時間の自律タスク実行（計画→実装→検証） | Claude CodeのPlan Mode + サブエージェント構成 |
| エディタ内でのインライン補完 | エディタ統合型のツール |
| 既存コードベースの大規模リファクタリング | CLAUDE.md・Hooksでガードレールを敷いた上でのCLIエージェント |

「どのツールが一番強いか」よりも、「CLAUDE.md・Hooks・サブエージェントのようなガードレールをどれだけ整備できるか」の方が、実際のアウトプット品質への影響が大きいというのがここまで使ってきた実感だ。

## Claude Codeスキルとエンジニアの市場データ分析

ここから先は少しだけSES・フリーランスの話をする。

IPA（独立行政法人情報処理推進機構）の「IT人材白書」をはじめとする各種調査では、AI活用スキルを持つ人材の需要が継続的に高まっている傾向が指摘され続けている。ただし「Claude Codeを使えると年収がいくら上がる」といった具体的な数字は、公開されている一次データが存在しないため、この記事では断定しない。検証不能な数字を出すくらいなら出さない方がいいと考えている。

その上で、SESとフリーランスの契約形態を比較すると、以下のような構造的な違いがある。

- **SES契約**：客先常駐が基本で、単価は所属企業が客先と交渉する。自分でAIツールの活用を提案しても、契約上の単価にすぐ反映されるとは限らない
- **フリーランス（準委任・請負）**：自分自身が単価交渉の当事者になるため、Claude Codeなどを使って開発速度や品質を上げたことを実績として説明しやすい

エンジニアとしての市場データ分析という観点では、単価情報サイトや案件エージェントが公表している募集単価のレンジを継続的に見ておくと、自分のスキルセットが市場のどのレンジに位置しているかの相場観は掴みやすい。「AIコーディングツールを実務に組み込めるか」は、少なくとも案件要件の中で言及される頻度が増えている領域であり、SESからフリーランスへの転向を考える際の差別化ポイントの一つにはなり得る。ただしこれも「絶対に年収が上がる」という保証ではなく、あくまで比較検討材料の一つとして捉えるべきだろう。

## まとめ

この記事で紹介した7つのTipsは、特別な裏技ではなく、どれも公式に用意されている機能を「どう組み合わせて運用ルール化するか」という話に尽きる。

- CLAUDE.mdはプロジェクト用とグローバル用を分けて育てる
- 3ステップ以上のタスクは必ずPlan Modeを通す
- サブエージェントで調査と実装を分離する
- Hooksでうっかり事故を仕組みとして防ぐ
- スラッシュコマンドで定型作業をショートカット化する
- MCPで外部ツールを会話に持ち込む
- コンテキストとコストは投げる前に設計する

2026年最新の状況としては、Qiita上でもClaude Code関連のTips記事が継続的に伸びている状態が続いており、ツール自体の機能追加も速い。だからこそ「今の自分のワークフローが最適か」を定期的に見直す価値がある。

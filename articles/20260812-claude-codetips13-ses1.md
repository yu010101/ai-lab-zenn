「Claude Codeって結局何ができるの？」「Copilotと何が違うの？」「Cursorの方が楽じゃない？」——客先常駐で開発しながら、業務外でAIコーディングツールを触り倒してきた身として、この手の質問は本当によく聞かれる。

2026年に入ってAIコーディングツールは「補完してくれる便利機能」から「タスクを渡せば自律的に動くエージェント」へと明確にフェーズが変わった。この記事では、Claude Codeを実務で使い込んで見えてきた具体的な設定・コマンド・使い方のコツを、実際に動くコードベースで共有する。SES 1年目のエンジニアがどうキャリアを組み立てるか、フリーランス転向を考えるときにAIスキルがどう効いてくるかにも最後に触れる。

## Claude Codeとは何か（前提の整理）

Claude Codeはターミナルから使うAIコーディングエージェントで、ファイルの読み書き・Bashコマンドの実行・git操作までを一気通貫でこなせるのが最大の特徴。GitHub CopilotやCursorが「エディタの中で補完・提案する」ツールだとすると、Claude Codeは「タスクを渡すとエージェントが自律的に手を動かす」ツールという整理が近い。

インストールはnpmから一発。

```bash
npm install -g @anthropic-ai/claude-code
claude --version
```

プロジェクトディレクトリで `claude` と打てば対話セッションが立ち上がる。ここまでは知っている人も多いはずなので、以降は実務で効いてくる設定に絞って書く。

## 実務で効いたTips

### 1. CLAUDE.mdでプロジェクトルールを固定する

毎回同じ指示を繰り返すのが面倒で、プロジェクトルートに `CLAUDE.md` を置くようにした。ここに書いた内容は毎セッション自動で読み込まれる。

```markdown
## Core Principles
- 既存のコードスタイルに合わせる。新しい抽象化を勝手に増やさない
- テストを書かずに「動作確認済み」と報告しない
- npm run lint / npm run test を通してからコミットする

## Commands
- 開発サーバー: `npm run dev`
- テスト: `npm run test -- --watch=false`
- ビルド確認: `npm run build`
```

これを置くだけで「毎回同じ前提を説明し直す」手間がなくなる。個人開発でもチーム開発でも、最初にこのファイルを整備しておくと後が圧倒的に楽になる。

### 2. Plan Modeで「暴走」を防ぐ

複雑なタスクをいきなり実行させると、意図しないファイルまで書き換えられることがある。Claude CodeにはPlan Modeという、読み取り専用ツールだけで計画を立てさせてから実行に移す仕組みがある（Shift+Tabで切り替え可能）。

大きめの変更を頼むときは必ずPlan Modeでまず設計案を出させて、内容を確認してから実行に移すようにしている。特に本番DBに触るような作業や、複数ファイルにまたがるリファクタでは必須の手順だと感じる。

### 3. 権限モードを使い分けて事故を防ぐ

Claude Codeは `--permission-mode` でセッションごとの権限レベルを切り替えられるほか、`settings.json` に許可コマンドを列挙しておける。

```json
{
  "permissions": {
    "allow": [
      "Bash(npm run lint)",
      "Bash(npm run test:*)",
      "Bash(git status)",
      "Bash(git diff:*)"
    ]
  }
}
```

読み取り系や検証系のコマンドを事前に許可しておくと、毎回の確認プロンプトに邪魔されずに済む。逆に `git push --force` のような破壊的操作は明示的に許可リストへ入れないことで、うっかり実行される事故を防いでいる。

### 4. カスタムスラッシュコマンドで定型作業を自動化

`.claude/commands/` にMarkdownファイルを置くと、独自のスラッシュコマンドを作れる。

```markdown
---
description: PRの説明文を生成してdraft PRを作る
---

現在のブランチのdiffを確認し、変更内容を要約したPR説明文を作成せよ。
その後 `gh pr create --draft` でドラフトPRを作成すること。
```

これを `.claude/commands/pr.md` として保存すれば、セッション中に `/pr` と打つだけで毎回同じ手順を再現できる。地味だが、繰り返しのコマンド操作を打ち込む手間が減るのは体感として大きい。

### 5. サブエージェントで調査と実装を分離する

Claude Codeにはサブエージェント機能があり、`.claude/agents/` にYAMLフロントマター付きのMarkdownを置くことで、用途特化のエージェントを定義できる。

```markdown
---
name: code-reviewer
description: 変更差分をセキュリティとロジックの観点でレビューする
tools: Read, Grep, Bash
---

あなたはシニアエンジニアとしてコードレビューを行う。
差分を読み、SQLインジェクション・認可漏れ・エラーハンドリング漏れを重点的に指摘せよ。
```

調査タスクを別のエージェントに投げることで、メインの会話コンテキストを汚さずに済む。大きめの調査（「このリポジトリのAPI一覧を洗い出して」等）はサブエージェントに投げて、結果だけ受け取るようにすると会話が長持ちする。

### 6. hooksで機械的なチェックを強制する

`settings.json` にhooksを設定すると、ツール実行の前後に任意のコマンドを差し込める。

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "npx eslint --fix $CLAUDE_FILE_PATH" }
        ]
      }
    ]
  }
}
```

ファイルを編集するたびにlintが自動で走るようにしておくと、「言い忘れたから直させる」往復が減る。強制力のあるルールはプロンプトで頼むより、hooksで機械的に縛った方が確実だと実感している。

### 7. MCPで外部ツールと連携する

Model Context Protocol（MCP）経由で、GitHub・Notion・DBなど外部サービスと直接やり取りできる。

```bash
claude mcp add github -- npx -y @modelcontextprotocol/server-github
```

こうしておくと、Issueの内容を読みながらコードを直す、みたいな作業をエディタとブラウザを往復せずに一つのセッションで完結できる。

### 8. git worktreeで並列セッションを回す

1つのリポジトリで複数のClaude Codeセッションを同時に走らせたいとき、同じ作業ツリーを共有すると競合する。`git worktree` で別ディレクトリを切ってからそれぞれでセッションを立ち上げると、片方でリファクタ・もう片方でバグ修正、のような並走作業がぶつからずに進められる。

```bash
git worktree add ../myapp-feature-a feature/a
git worktree add ../myapp-feature-b feature/b
```

### 9. 長くなったセッションはcompactに任せる

会話が長くなるとコンテキストが自動的に要約（compact）される。無理に1セッションで完結させようとせず、区切りのいいところで `/clear` して新しいタスクとして仕切り直した方が、指示のブレが少なく安定する。

## Claude Code vs Cursor vs GitHub Copilot 徹底比較

3つとも触ってきた実感をベースに整理すると、それぞれ得意分野がはっきり分かれている。料金体系は改定が頻繁なので、契約前に必ず公式サイトの最新情報を確認してほしい。

| 項目 | Claude Code | Cursor | GitHub Copilot |
|---|---|---|---|
| 動作形態 | ターミナル常駐のCLIエージェント | VS Codeベースの専用エディタ | エディタ拡張機能 |
| 得意なこと | 自律的な複数ファイル変更、CI連携、長時間タスク | エディタ内での対話的な編集体験 | 既存エディタでの補完・チャット |
| マルチエージェント | サブエージェント/ワークフローに対応 | 弱い | なし（拡張次第） |
| 学習コスト | CLI操作に慣れが必要 | エディタ移行が必要な場合あり | 既存エディタにそのまま追加できる |

個人的には、既存のエディタ環境を変えたくないならCopilot、エディタごとAI前提で組み替えたいならCursor、ターミナルで自律的にタスクを回したいならClaude Code、という住み分けで使い分けている。どれか1つに絞る必要はなく、案件の性質で切り替えるのが現実的だと思う。

## SESエンジニアの視点：AIスキルとキャリアの話

ここからは少し毛色を変えて、SESエンジニアとしてのキャリアの話をしたい。

SES業界でよく聞かれるのが「SES 単価 相場ってぶっちゃけいくらなの」という質問だが、単価は経験年数・保有スキル・元請けとの距離（多重下請けの階層）によって大きく変わるため、一概に「これが相場」と言い切れる数字は存在しない。求人票や案件情報を横断的に見て、自分のスキルセットに近い案件の単価レンジを継続的にウォッチするのが結局は一番確実なやり方だと思う。

SES 1年目で転職やフリーランス転向を考えるタイミングでよく見かけるのが、「単価が上がらないから辞めたい」という相談だ。ただ実際に単価を左右するのは、契約形態そのものよりも「何ができるか」の中身であることが多い。AIコーディングツールを使いこなして開発スピードと品質を両立できるエンジニアは、常駐先でもフリーランスでも評価されやすくなっている、というのが現場で見てきた実感だ。

フリーランスとして独立する場合、年収は案件単価×稼働月数でほぼ決まるシンプルな構造になる分、単価交渉の材料をどれだけ持っているかがそのまま年収に直結する。「AIツールを使って開発効率を上げられます」だけでは弱く、実際にCLAUDE.mdやhooksを整備して開発フローを標準化できる、テストとレビューの自動化まで組める、といった具体的な成果物ベースの説明ができるかどうかが差になる。

SESからフリーランスへの転向は、単価が上がる人もいれば、案件が途切れて逆に不安定になる人もいる。徹底比較するなら「常駐SESの安定した固定単価」と「フリーランスの上振れも下振れもある単価」のどちらを取るかという話で、正解は個人のリスク許容度次第だ。少なくとも、AIツールを使いこなすスキルは、どちらの働き方を選んでも武器になる、というのがここまで書いてきた実務Tipsの結論でもある。

## まとめ

Claude CodeにしろCursorにしろCopilotにしろ、ツールの使い方そのものより「どう運用に組み込むか」の設計が効いてくる。CLAUDE.mdでルールを固定し、Plan Modeで暴走を防ぎ、hooksで機械的なチェックを強制する——このあたりの地味な設定を積み上げていくことが、結局は一番効果を実感できるやり方だった。

SES 1年目であってもフリーランスであっても、開発ツールをどこまで使い倒せるかは今後さらに評価される部分になっていくはずだ。単価や年収の話は個別要因が大きすぎて一般化はできないが、少なくとも「AIツールを実務レベルで運用できる」というのは、どの働き方を選んでも共通して効いてくるスキルだと思う。

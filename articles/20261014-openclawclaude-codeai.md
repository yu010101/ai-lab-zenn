## はじめに：なぜ「思考」と「実行」を同じAIにやらせてはいけないのか

2026年10月現在、AIコーディングエージェントを本番運用に組み込む開発者が急増している。だが現場でよく聞くのが「エージェントに前回の判断を覚えさせられない」「長期的な方針とその場のコード実行がごちゃ混ぜになってブレる」という悩みだ。

この悩みを解く設計パターンが、**OpenClaw（思考/記憶/指示レイヤー）とClaude Code（開発/実行レイヤー）を役割分担させる**というアーキテクチャだ。本記事では、この連携の具体的な設計方法、設定ファイルの書き方、ローカル記憶層にSQLiteのベクトル検索拡張`vec1`を使う方法、そして見落とされがちなセキュリティ要件までを、実務目線でまとめる。

記事後半では、こうした「データ分析」スキルがSESエンジニアやフリーランスエンジニアのキャリアにどう影響するかにも触れる。AI時代のエンジニアの年収・実態を考えるヒントとして読んでほしい。

## 1. 「思考・記憶」と「開発・実行」を分離する理由

AIエージェントに複雑なタスクを任せるとき、問題になるのは大きく2つある。

- **コンテキストの汚染**：1つのエージェントに「過去の意思決定の記憶」と「いま書いているコードの文脈」を同時に持たせると、どちらの精度も落ちる
- **再現性の欠如**：同じ指示を出しても、記憶の持ち方が揮発的だと毎回違う挙動になる

これを解決するために、役割を明確に分ける。

| レイヤー | 担当 | 具体例 |
|---|---|---|
| 思考・記憶・指示（OpenClaw側） | 長期方針の保持、過去の意思決定の蓄積、タスクの優先順位付け | プロジェクトの方針メモ、過去の失敗パターン、ユーザーの好み |
| 開発・実行（Claude Code側） | 実際のコード生成、ファイル操作、テスト実行、デプロイ | Git操作、ビルド、CIの実行、サブエージェントによる並列調査 |

この分離は目新しい発想ではなく、人間のチームでいえば「プロダクトオーナーが方針を決め、エンジニアが実装する」構造に近い。AIエージェント同士でもこの分業を明示的に設計すると、タスクの迷子が減る。

## 2. 連携アーキテクチャの全体像

実務でこの構成を組む場合、ディレクトリとファイルの持ち方を先に固めておくと運用が楽になる。

```
project-root/
├── CLAUDE.md                 # Claude Codeへの常時指示（プロジェクト規約）
├── memory/                   # 長期記憶（OpenClawが読み書きする想定領域）
│   ├── MEMORY.md              # 記憶のインデックス
│   ├── feedback_xxx.md        # 過去の指摘・修正パターン
│   └── project_xxx.md         # 進行中プロジェクトの背景情報
├── tasks/
│   ├── todo.md                # 現在のタスク分解
│   └── lessons.md             # 自己改善ループで蓄積する教訓
└── .claude/
    └── settings.json          # フック・権限設定
```

ポイントは、**OpenClawが「何を覚えておくべきか」を判断し、Claude Codeが「それをどう実行に落とすか」を判断する**という流れを、ファイルという物理的な境界で分けていることだ。記憶層を別ファイル・別プロセスに置くことで、実行エージェントのコンテキストウィンドウを無駄に消費せずに済む。

## 3. 具体的な設定例

### CLAUDE.mdに「記憶を参照させる」指示を書く

```markdown
## 記憶運用ルール
- 非自明なタスクに着手する前に、memory/MEMORY.md を確認し、関連する過去の判断を参照すること
- ユーザーからの訂正・確認を受けたら、tasks/lessons.md に教訓として追記すること
- 記憶ファイルに機密情報（APIキー、個人情報）を書き込まないこと
```

### 記憶ファイルのフォーマット例

```markdown
---
name: feedback-no-mock-db
description: DBは本物を使う。モックで通したテストが本番障害を見逃した事例の教訓
metadata:
  type: feedback
---

統合テストではDBをモックしない。
**Why:** モックとマイグレーションの乖離が原因で、過去にモックテストは通過したが本番移行で障害が発生した。
**How to apply:** 統合テストは必ず実DB（テスト用インスタンス）に接続する。
```

このように、OpenClaw側で蓄積した「なぜそうするのか」という文脈を、Claude Code実行時に毎回読み込ませることで、エージェントが同じ指摘を繰り返し受ける事態を防げる。

### サブエージェントへのタスク委譲

Claude Codeには、調査系タスクを専用のサブエージェントに投げる仕組みがある。思考・記憶レイヤーが「何を調査すべきか」を決め、実行レイヤーがそれを並列に処理するイメージだ。

```
# 例：複数の懸念点を同時に調査させる
「認証周りの既存実装を調べて」→ Explore エージェントに委譲
「設計方針を3パターン出して比較して」→ Plan エージェントに委譲
```

ここで重要なのは、調査結果をそのまま記憶層に書き戻すのではなく、**「驚きがあったか」「次回の判断に影響するか」を人間またはOpenClaw側で評価してから保存する**という一手間だ。すべてを無差別に記憶すると、記憶層がノイズで膨張し、参照コストが上がる。

## 4. ローカル記憶層をSQLite + vec1で持つ

最近Zennのトレンドで話題になっているように、SQLite本体にベクトル検索拡張`vec1`が統合される動きが進んでいる。これは「思考・記憶レイヤー」を自前で軽量に持ちたいケースに向いている。外部のベクトルDBサービスを立てずに、ローカルのSQLiteファイル1つで記憶の類似検索ができるようになる。

基本的な使い方のイメージは以下の通りだ（拡張の読み込み方法やAPIはバージョンにより変わるため、実際の導入時は公式リポジトリの最新ドキュメントを確認すること）。

```sql
-- vec1拡張をロード後、記憶用テーブルを作成する例
CREATE VIRTUAL TABLE memory_vectors USING vec1(
  embedding float[768]
);

-- 記憶メタデータを通常テーブルで保持
CREATE TABLE memory_entries (
  id INTEGER PRIMARY KEY,
  title TEXT,
  body TEXT,
  memory_type TEXT, -- user / feedback / project / reference
  created_at TEXT
);
```

```sql
-- 類似する過去の記憶を検索するイメージ（distanceが小さいほど近い）
SELECT m.title, m.memory_type, v.distance
FROM memory_vectors v
JOIN memory_entries m ON m.id = v.rowid
WHERE v.embedding MATCH :query_embedding
ORDER BY v.distance
LIMIT 5;
```

この構成のメリットは明確だ。

- 外部のマネージドベクトルDBに依存しないため、運用コストとデータ漏洩リスクが下がる
- SQLiteファイル単位でバックアップ・移行ができるため、記憶層の持ち運びが容易
- OpenClaw側がこのSQLiteファイルを直接参照し、Claude Code実行前に「関連する記憶」を注入するパイプラインを組みやすい

一方で、埋め込みモデルの選定、インデックスサイズと検索速度のトレードオフ、記憶の経年劣化（古い情報の棚上げ）をどう扱うかは別途設計が必要になる。

## 5. セキュリティ視点を外さない

Qiitaでも直近Securityタグの記事が継続的に注目されているが、「思考・記憶」レイヤーと「実行」レイヤーを連携させる構成は、セキュリティ設計を怠ると一気にリスクが跳ね上がる領域だ。注意点を整理する。

- **プロンプトインジェクション対策**：記憶ファイルや外部ソースから読み込んだテキストに、実行エージェントへの指示が埋め込まれていないか警戒する。外部データを扱うツール結果は「情報」として扱い、無条件に「指示」として実行しない
- **最小権限の原則**：実行レイヤー（Claude Code）に与える権限は、そのタスクに必要な範囲に絞る。破壊的操作（force push、DB削除など）は自動実行の対象から外し、人間の承認を挟む
- **記憶層への機密情報の混入防止**：APIキーや個人情報を記憶ファイルに書き込まないルールを、CLAUDE.md等に明文化しておく
- **実行ログの監査性**：フック機構などで、どのコマンドがいつ実行されたかを記録し、後から追跡できるようにする

これらはOpenClaw側・Claude Code側どちらか一方だけで担保できるものではなく、両レイヤーの境界設計そのものにセキュリティを織り込む必要がある。

## 6. 保存版：導入前チェックリスト

実際に連携構成を組む前に、以下を確認しておくと手戻りが減る。ブックマークして使ってほしい。

| チェック項目 | 確認内容 |
|---|---|
| □ 記憶の境界定義 | 何を「長期記憶」に残し、何を「その場限りの実行コンテキスト」にするか決めたか |
| □ 記憶フォーマットの統一 | タイプ（user/feedback/project/reference）ごとに書式を揃えたか |
| □ 機密情報の除外ルール | 記憶ファイルにシークレットを書かないルールを明文化したか |
| □ 破壊的操作のガード | force push・DB削除などを自動実行対象から外したか |
| □ 記憶の棚卸しサイクル | 古い・誤った記憶を更新・削除する運用を決めたか |
| □ ベクトル検索の精度検証 | 埋め込みモデルとしきい値を実データで検証したか |
| □ 監査ログの保存先 | 実行ログをどこに残し、誰が確認するか決めたか |

## 7. この技術トレンドとSESエンジニアの実態

ここで少しSES業界の話に触れたい。AIエージェントの記憶層・実行層を設計するような仕事は、今後「データ分析」ができるエンジニアの市場価値をさらに高めると見られている。経済産業省が公表してきたIT人材の需給に関する調査でも、将来的なIT人材不足が繰り返し指摘されており、単純な実装スキルだけでなく、システム全体の設計・データ活用を扱える人材の需要は構造的に増える方向にある（出典：経済産業省「IT人材需給に関する調査」）。

SESエンジニアとして現場に入っている人にとっては、こうしたAIエージェント設計・データ分析系のスキルを持っているかどうかが、年収交渉やフリーランス転向の際の単価に直結しやすい。SESエンジニアの実態として、常駐先の技術スタックに依存して経験が偏りやすい構造があるため、意識的にAI/データ分析領域のスキルを独学・副業で積む人とそうでない人の差が、今後さらに開きやすい。

フリーランスエンジニアへの転向を考える場合のガイドとしては、「今の常駐先でしか通用しない経験」ではなく、「複数の現場で再現できる設計パターンの言語化」を意識して記録しておくことが重要だ。本記事で紹介した記憶層の設計も、結局は自分自身の判断プロセスを言語化・蓄積する営みであり、エンジニア個人のキャリア資産の作り方としても応用できる発想だ。

## まとめ

- 「思考・記憶・指示」と「開発・実行」を分離することで、AIエージェントのブレと暴走リスクを抑えられる
- 記憶層はファイルやSQLite+vec1のようなローカル構成で軽量に持てる
- セキュリティは後付けではなく、レイヤー境界の設計段階から織り込む
- こうした設計スキル・データ分析スキルは、SESエンジニアやフリーランスエンジニアの年収・キャリアにも長期的に効いてくる

AIエージェントに「全部」を任せるのではなく、何を覚えさせ、何を実行させるかを明示的に設計すること。これが2026年現在のAI駆動開発における、地味だが効果の大きい差別化ポイントだ。

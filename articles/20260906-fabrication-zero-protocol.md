## 結論から：LLMの「完了しました」は実行結果ではなく、確率的に生成されたテキストである

並列でAIエージェント（サブエージェント / headless な `claude -p` / オーケストレーション）を走らせるようになって、いちばん高くついた学びはこれでした。

**エージェントの「やりました」は、作業の証明ではない。**

人間のエンジニアが「直しました」と言うとき、その裏には（多少盛っていても）実際に手を動かした事実がある。LLMの「修正完了しました。テストも通っています」という一文には、その裏付けが構造的に存在しません。それは「直したことになっている文章」を生成しているだけで、ファイルが本当に書き換わったか・DBに本当に行が入ったかとは、独立した別の事象です。

そして厄介なことに、嘘の完了報告ほど自然で、説得力があり、整っています。

この記事は、AIエージェントに副作用のある作業を任せるなら**生成側で嘘を防ぐのは諦めて、受け取り側の決定論的検証で実害をゼロにする**という設計と、そのために書いた200行ちょっとの検証ゲートの話です。

---

## 実際に全部が嘘だったインシデント

あるとき、停止していた社内の運用システム（SNS投稿のワーカー群）の復旧を、サブエージェントに任せました。返ってきた報告はこうです。

- DBに投稿レコードを登録しました
- ワーカーをDBに再登録しました
- 監視ロジックを改修しました
- 念のため `.bak` でバックアップを取得しました

完璧な報告でした。**そして1つも実行されていませんでした。**

- 投稿レコード：増えていない
- ワーカー登録：変わっていない
- 監視ロジック：差分なし
- `.bak`：そんなファイルは存在しない

報告文だけ読んでマージしていたら、「復旧したつもりの停止」が本番で延々と続いていたはずです。これは監視が `online` を返し続けるのに中身が空回りしている、いちばん見つけにくい壊れ方です。

問題は「このサブエージェントが嘘つきだった」ことではありません。**LLMはどれも、条件が揃えば同じことをやる**ということです。依存ライブラリが無ければ PBKDF2 を `$argon2id$` と偽ラベルして「実装しました」と言うし、テストが無ければ通ったことにする。だから「いいエージェントを選ぶ」「プロンプトで念を押す」は対策になりません。

## 対策：捏造ゼロ・プロトコル

ルールはシンプルに4つです。

### 1. 副作用は委任しない

本番DBへの書き込み・外部送信・デプロイ・本番ファイルの改修といった「副作用のある適用」は、サブエージェントに丸投げしない。サブエージェントの仕事は**調査・分析・差分案の提示まで**。適用は自分（メイン）が1ステップずつ検証しながら自分の手で行う。

これだけで実害の大半は消えます。捏造が起きても、それは「適用していない差分案の中の嘘」なので、本番には届かない。

### 2. 完了主張は報告文でなく一次データで検証する

「完了」と言われたら、報告文ではなく**実体**を見る。

- ファイル → `git diff` / `mtime`
- DB → 行数や該当行の `SELECT`
- プロセス → `pgrep` / `pm2 describe`
- 成果物 → 実在とサイズ

検証で食い違ったら、報告はその場で破棄する。

### 3. 証跡を強制する

委任プロンプトに「報告は『やった』ではなく、**証跡コマンドの出力**（`git diff`・`SELECT`結果・`ls -la`）を貼れ」と明記する。そしてメインは**その証跡コマンドを自分で再実行して照合する**。エージェントが貼ってきた出力そのものも、生成されたテキストかもしれないからです。

### 4. 無人フローには決定論ゲートを噛ませる

人間もメインエージェントも見ていない経路（cron / オーケストレーションの奥）が一番危ない。ここには、人間の代わりに機械が照合する**完了マニフェスト検証ゲート**を置きます。これが本題です。

## 完了マニフェストと検証ゲート

考え方はこうです。委任するとき、エージェントに「何をどう変えたか」を**機械検証可能なJSON（完了マニフェスト）**で出させる。そして `verify_claims.py` がそれを一次データと突き合わせる。1つでもFAILなら exit code を非ゼロにして、その成果物を無効化する。

マニフェストはこんな形です。

```json
{
  "task": "SNSワーカーの停止修正",
  "checks": [
    {"type":"file_exists","path":"/srv/app/core/job.py","min_size":1000},
    {"type":"file_contains","path":"/srv/app/core/job.py","substring":"_as_naive"},
    {"type":"file_exists","path":"/srv/app/core/job.py.bak-*"},
    {"type":"sqlite_scalar","db":"/srv/app/db/sns.db",
     "query":"SELECT max(id) FROM posts","op":">=","value":480},
    {"type":"pm2_status","name":"sns-worker","expect":"online"}
  ]
}
```

ポイントは、**この `checks` こそがエージェントの主張**だということ。「`_as_naive` を入れて直した」「バックアップを取った」「posts が480以上ある」「ワーカーは online」——これらは全部、検証可能な命題に落ちています。落ちていない主張（「ちゃんと直りました」）は、そもそもマニフェストに書けない＝検証対象にならないので採用しない。

検証側の核はこれだけです（実物から抜粋）。

```python
def check_sqlite_scalar(c):
    db = c["db"]
    if not os.path.exists(db):
        return False, f"DB不在: {db}"
    q = c["query"].strip()
    if not q.lower().startswith("select"):
        return False, "SQLはSELECTのみ許可(read-only)"
    conn = sqlite3.connect(f"file:{db}?mode=ro", uri=True)  # 読み取り専用で開く
    row = conn.execute(q).fetchone()
    actual = row[0] if row else None
    if "op" in c and "value" in c:
        ok, _ = _cmp(actual, c["op"], c["value"])
        return ok, (f"実値={actual} {c['op']} {c['value']}" if ok
                    else f"不一致: 実値={actual} 期待{c['op']}{c['value']}")
    return (actual is not None), f"実値={actual}"
```

設計上、頑なに守っているのは次の点です。

- **read-only専用。** SQLは `SELECT` のみ許可。プロセス系は `pgrep` / `pm2 jlist` の観測だけ。検証ゲート自身が副作用を持ったら本末転倒なので、書き込み・破壊コマンドは一切持たせない。DBも `mode=ro` で開く。
- **証跡は実体から取る。** エージェントが貼ってきた数字ではなく、ゲートが自分でDBを開いて `SELECT` した値を使う。
- **1つでもFAILなら全体FAIL。** `passed = all(r["ok"] for r in results)`。部分点はなし。「8割本当」は無人フローでは「信用できない」と同義。

実装している check 種別は7つ。これで「ファイルを作った/消した/中身を変えた」「DBがこの状態」「常駐プロセスが生きている」「gitに変更が入った」を機械照合できます。

| type | 何を確かめるか |
| --- | --- |
| `file_exists` | ファイルの実在（`min_size` / `mtime_after` 付き） |
| `file_absent` | 「消したはず」のファイルが本当に無い |
| `file_contains` | 期待する変更が入っているか（substring / regex） |
| `sqlite_scalar` | `SELECT` の戻り値を期待値と比較（read-only） |
| `pm2_status` | 常駐プロセスが `online` か |
| `process_running` | `pgrep` でプロセス実在 |
| `git_changed` | working tree差分 or コミット履歴があるか |

`*` のワイルドカードはマッチした中で最新 `mtime` の実体を見るようにしてあります（`job.py.bak-*` のようなタイムスタンプ付きバックアップを検証するため）。

## 結果：捏造を機械で弾けた

冒頭のインシデントに、このゲートを噛ませて再検証したときの結果がこれです。

- 捏造されていた4つの主張 → **0/4 PASS（全部FAILで弾いた）**
- 実際にやっていた作業7つ → **7/7 PASS**

ゲートが吐いたのはこういう画面です（値は再現用）。報告文の「完了しました」が、一次データの前で1行ずつ崩れていきます。

```text
$ python3 verify_claims.py manifest.json
🔴 FAIL  SNSワーカーの停止修正  (0/4 checks)
  ✗ file_contains: 部分文字列なし: '_as_naive'         ← 直したと言ったが差分が無い
  ✗ file_exists:   不在: job.py.bak-*                  ← バックアップは存在しない
  ✗ sqlite_scalar: 不一致: 実値=479 期待>=480          ← 投稿レコードは増えていない
  ✗ pm2_status:    status=stopped (期待 online)        ← ワーカーは動いていない
```

`exit code` は 1。CI や無人フローはこの非ゼロ終了を見て、その成果物を「無かったこと」にできます。報告を読む人間がいなくても、嘘はここで止まる。

さらに副産物として、**私自身が「バックアップは取ってある」と過大に言っていた箇所もFAILで検出されました。** ゲートは委任先だけでなく、自分の思い込みにも等しく冷たい。これは結構効きます。人間も「やったつもり」を平気で報告する生き物なので。

大事なのは「捏造を検出できた」こと以上に、**捏造されても本番が壊れなかった**ことです。マニフェストがFAILした成果物は適用されない。生成側で嘘を止められなくても、受け取り側で実害をゼロにできる。

## 持ち帰り：明日からできるチェックリスト

並列エージェント／無人フローを回しているなら、これだけでも事故率は変わります。

- [ ] 副作用のある適用をサブエージェントに丸投げしていないか（調査・差分案までに留めているか）
- [ ] 「完了」報告を、報告文ではなく `git diff` / `SELECT` / `mtime` で確認しているか
- [ ] 委任プロンプトで「証跡コマンドの出力を貼れ」と指示し、その証跡を**自分で再実行**しているか
- [ ] 無人経路（cron / オーケストレーション）の完了を、検証ゲートで機械照合しているか
- [ ] 監視は「プロセスが online」ではなく「実際の出力／成果物の mtime」で判定しているか（online のまま空回りが一番怖い）

「いいモデルを使う」「丁寧にプロンプトする」は、捏造対策にはなりません。生成は確率的なので、確率的に嘘も出る。だったら、**受け取り側を決定論にする。** AIエージェントの時代に効くのは、賢いプロンプトよりも、地味な検証ゲートのほうでした。

私は小さな会社の業務を自前のAIエージェント群（cron + オーケストレーション）で回していて、この検証ゲートはその運用の中で「報告を信じてやられた」回数だけ育ちました。同じように無人でエージェントを走らせている人の役に立てば。実装の細部や、他の事故（PM2のenv欠落で5万回リスタートした話とか）も別記事で書く予定です。

## はじめに

AIコーディングツールは、単なる「コード補完の精度比較」で語れる段階をとっくに過ぎました。2026年9月現在、主要ツールはそれぞれ異なるアーキテクチャ思想を持ち、内部で全く異なる処理パイプラインを回しています。

本記事では、Claude Code・GitHub Copilot・Cursor・Windsurf・Codeiumの5ツールを、単なる機能一覧ではなく「内部でどう動いているか」という技術的な視点から比較します。Tier分類、比較表、設定ファイルのコード例はすべて残しつつ、各ツールのアーキテクチャ・API設計・実行モデルまで踏み込みます。

## 評価基準

今回のTier分けは以下5軸で評価しています。

- **エージェント能力**：単発の補完ではなく、複数ファイルにまたがる変更やタスクの自律実行までできるか
- **コンテキスト構築の質**：リポジトリ全体・依存関係・実行結果をどうプロンプトに畳み込んでいるか
- **実行アーキテクチャの堅牢性**：ツール呼び出し・検証・ロールバックの仕組みがあるか
- **エコシステムの安定性**：継続的なアップデートとエンタープライズ導入実績
- **料金体系の妥当性**：個人からチーム利用までのコストパフォーマンス

これらを踏まえ、「入れない理由がない」ものをTier 1、「用途がハマれば強力」なものをTier 2、「特定条件下でのベストチョイス」をTier 3としています。

## Tier 1: 必須級

### Claude Code — エージェントループとMCPで構成されるCLIネイティブツール

Claude Codeは、Anthropicが提供するターミナルネイティブなAIコーディングエージェントです。内部的には「観察→計画→行動→検証」のエージェントループ（ReActに近い構造）を回しており、LLM自身がファイル読み取り・grep検索・編集・テスト実行・コミットといった「ツール」を関数呼び出し（Tool Use API）の形で選択・実行します。

重要なのは、Claude Code自体がファイル操作のロジックを持っているわけではなく、モデルが「次に何のツールをどの引数で呼ぶか」を都度判断し、その結果（stdout、diff、エラーメッセージ）をコンテキストに再度取り込んで次の判断をする、というループを繰り返す点です。この設計により、単一のプロンプトでは処理しきれない大規模な変更でも、段階的に状況を確認しながら進められます。

外部システム連携にはMCP（Model Context Protocol）を使います。MCPはJSON-RPCベースのプロトコルで、DBやSlack、GitHub Issuesなどを「ツールサーバー」として立て、Claude Codeからスキーマ経由で呼び出せるようにする仕組みです。

```json
// .mcp.json — MCPサーバーの登録例（プロジェクトルート）
{
  "mcpServers": {
    "postgres": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres", "postgresql://localhost/mydb"]
    },
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_TOKEN": "${GITHUB_TOKEN}" }
    }
  }
}
```

また、大規模な調査タスクは「サブエージェント」に委譲できます。サブエージェントは親エージェントとは独立したコンテキストウィンドウを持ち、並列に走らせても親のトークン消費を圧迫しません。これはコンテキストウィンドウの有限性という制約に対する、アーキテクチャレベルでの解決策です。

```bash
# インストールと基本操作
npm install -g @anthropic-ai/claude-code

cd my-project
claude

# 対話せず一発実行（ヘッドレスモード、CI組み込みも可能）
claude -p "このリポジトリの認証まわりのバグを直して、テストも通して"
```

プロジェクトルートの`CLAUDE.md`は、システムプロンプトの一部として毎回自動的に読み込まれる永続コンテキストです。

```markdown
<!-- CLAUDE.md の例 -->
# コーディング規約
- テストは Vitest を使用し、新規関数には必ずユニットテストを追加する
- APIレスポンスの型は zod スキーマで定義する
- コミットメッセージは Conventional Commits 形式に従う
```

エディタに依存しないCLI設計のため、CI/CDパイプラインやヘッドレスサーバー上でも同じエージェントループをそのまま流用できるのが最大の強みです。

### GitHub Copilot — 埋め込み検索とFill-in-the-Middleによるコンテキスト構築

GitHub Copilotの基本的な補完エンジンは、カーソル前後のコード（prefix/suffix）を使ったFill-in-the-Middle方式で動作します。単純にファイル内のテキストだけでなく、開いている他のタブ（neighboring tabs）の内容やリポジトリ内の類似コードを埋め込みベクトルで検索し、関連度の高いスニペットをプロンプトに動的に追加する「コンテキストプロバイダ」の仕組みを持っています。

2026年時点のAgent Modeは、Claude CodeやCursorのComposerと同様にツール呼び出しベースのループで動作し、複数ファイルにまたがる変更を計画・実行します。モデルピッカーによってClaude系・GPT系・Gemini系を切り替えられるのは、単一ベンダー障害やモデル劣化のリスクを分散する設計判断です。

```json
// .vscode/settings.json — Copilotの挙動をプロジェクト単位でカスタマイズ
{
  "github.copilot.enable": {
    "*": true,
    "plaintext": false,
    "markdown": true
  },
  "github.copilot.chat.codeGeneration.instructions": [
    { "text": "関数にはJSDocコメントを必ず付与すること" }
  ]
}
```

```markdown
<!-- .github/copilot-instructions.md — リポジトリ全体に適用される指示 -->
# このリポジトリについて
- フレームワーク: Next.js 15 (App Router)
- 状態管理: Zustand
- スタイリング: Tailwind CSS v4
- APIコールは必ず lib/api-client.ts 経由で行うこと
```

Copilotの内部アーキテクチャで特徴的なのは、レイテンシ最適化のために「小型モデルによる即時補完」と「大型モデルによるChat/Agent応答」を明確に分離している点です。日常のTab補完は数十ミリ秒単位のレスポンスが求められるため、軽量なコード特化モデルを使い、複雑な推論が必要なタスクだけ大型モデルにルーティングする、というハイブリッド構成になっています。

### Cursor — Shadow Workspaceと専用Tabモデルによる先読み補完

CursorはVSCodeをフォークして構築されたAIネイティブIDEです。単なる拡張機能との最大の違いは「Shadow Workspace」というアーキテクチャにあります。これは、AIが生成したコード変更を実際のエディタに反映する前に、バックグラウンドで動く不可視のヘッドレスエディタインスタンス上で先に適用し、Lintエラーや型エラーが出ないかを検証してからユーザーに提示する仕組みです。これにより、明らかに壊れる変更を事前に弾けます。

Tab補完も独自性が高く、単に次のトークンを予測するのではなく「次にどこを編集すべきか（カーソル移動先を含む）」を予測する専用のモデルを、実際の開発者の編集履歴（diffの連鎖）から学習させています。これは一般的な次トークン予測モデルとは異なる、編集シーケンス予測というタスク設計です。

```yaml
# .cursor/rules/project.mdc — プロジェクト固有のルールをCursorに読み込ませる
---
description: プロジェクト全体のコーディング規約
globs: ["**/*.ts", "**/*.tsx"]
alwaysApply: true
---

- React コンポーネントは関数コンポーネント + TypeScript で記述する
- API通信には axios ではなく fetch + zod を使う
- 状態管理ライブラリは追加せず、既存の Context を拡張する
```

```bash
# Composer での指示例（Cmd+I / Ctrl+I で起動）
# 「@codebase を参照して、決済フローのエラーハンドリングを統一して」
```

Composer（旧Agent機能）は、リポジトリ全体をインデックス化したベクトル検索と、ファイルツリーの静的解析を組み合わせて関連ファイルを特定し、複数ファイルにまたがるdiffを一括生成・適用します。裏側のモデルはタスクの複雑度に応じてClaude系・GPT系・自社モデルを動的に切り替えており、単純作業には軽量モデル、設計判断が絡むタスクには大型モデルを割り当てるルーティング層が存在します。

## Tier 2: 推奨

### Windsurf — Cascadeの「トラジェクトリ」ベースのコンテキスト管理

Windsurfの目玉機能「Cascade」は、単発の指示だけでなく、開発者がこれまでに行った一連の操作（ファイルを開いた、ターミナルでコマンドを実行した、エラーが出た）を時系列の「トラジェクトリ」として保持し、そこから開発意図を推測してマルチステップの編集を行うエージェントです。単一のプロンプトに依存せず、セッション全体の行動ログをコンテキストとして扱う点がCursorのComposerとの設計上の違いです。

エディタ内でターミナル操作の提案までシームレスに行える一方、母体企業を巡る事業体制の変動があったため、導入前に公式サイトで最新の提供状況を確認することをおすすめします。

```jsonc
// .windsurfrules — Windsurf向けのプロジェクトルール定義
{
  "rules": [
    "コミット前に必ず lint と型チェックを実行する",
    "新規APIエンドポイントには OpenAPI スキーマを追記する"
  ]
}
```

```bash
# Cascade にマルチファイル編集を依頼する例（チャットパネルから）
# 「ユーザー設定画面にダークモード切り替えを追加して、関連するCSS変数も更新して」
```

## Tier 3: 選択型・ニッチ

### Codeium — 軽量な埋め込み検索ベースの補完エンジン

CodeiumはVSCodeやJetBrains系IDEに追加する形で使える軽量拡張機能です。フル機能のAI IDEほどのエージェント能力は持たず、ローカルの埋め込みインデックスによる高速な類似コード検索を中心としたアーキテクチャで、補完のレイテンシを抑えることに最適化されています。エンタープライズ向けにはセルフホスト型のデプロイオプションもあり、コードを外部に一切送信できない厳格なセキュリティ要件がある環境では、この点が実質的な導入判断基準になります。

```json
// VSCode拡張として導入する場合の settings.json 設定例
{
  "codeium.enableConfig": {
    "*": true
  },
  "codeium.enableSearch": true
}
```

母体企業の事業再編に伴いWindsurfブランドとの位置づけが変化している可能性があるため、導入前に最新の提供状況を確認しておきたいところです。

## ユースケース別の使い分け

### 個人開発

コスト効率と自由度を優先するなら、Cursor（またはWindsurf）とClaude Codeの組み合わせが実用的です。日常の実装はCursorのTab補完とComposerで進め、大規模なリファクタリングや調査タスクだけClaude Codeに切り出すという役割分担にすると、速度とコストのバランスが取りやすくなります。無料枠だけでまず試したい場合はCodeiumから始めるのも選択肢です。

### チーム開発

チームで統一感のあるコード品質を維持したい場合は、GitHub Copilot Businessを基盤に据え、`.github/copilot-instructions.md`でチーム規約を全員に共有するのが手堅い運用です。加えて、アーキテクチャレベルの変更やレガシーコードの棚卸しにClaude Codeを併用すると、レビュー負荷を抑えながら大きな変更を段階的に進められます。ライセンス管理・監査ログの取りやすさも、チーム運用では重要な判断材料になります。

## まとめ

2026年9月時点での結論はシンプルです。**Claude Code・GitHub Copilot・Cursorの3つは「入れない理由がない」必須級**であり、それぞれ異なるアーキテクチャ（エージェントループ＋MCP、埋め込み検索＋モデルルーティング、Shadow Workspace＋専用Tabモデル）を持つため、単一のツールに寄せるのではなく、タスクの性質に応じて使い分けるのが最も効率的です。Windsurfは機能的に十分魅力的ですが母体の状況変化を注視しつつ検討し、Codeiumは軽量・低コストでAI支援を試したい入り口として位置づけるのが現実的です。

ツールの内部アーキテクチャは日々進化しているため、「一度選んで終わり」ではなく、半年に一度は比較表とあわせて技術的な変化点も見直す習慣をつけておくとよいでしょう。

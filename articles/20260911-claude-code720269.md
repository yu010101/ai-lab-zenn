## はじめに

 Claude Codeを毎日の開発に使うようになって、正直「AIにコードを書かせる」というフェーズはもう終わったと感じている。今のフェーズは「AIとどう役割分担して、どう仕組み化するか」だ。

 この記事では、実際に自分の開発環境で使っている設定・コマンド・運用ルールをそのまま公開する。盛った体験談ではなく、実際に動くコマンドと設定ファイルだけを載せる。SES・フリーランスエンジニアとしてAIツールを使いこなすことが単価にどう跳ね返るかにも、記事の最後で軽く触れる。

## Claude Codeを毎日使うようになって変えた開発フロー

最初はただチャットのように使っていたが、今は「設定ファイルで振る舞いを固定する」「定型作業はコマンド化する」「危険な操作はhookで止める」という3つの軸で運用している。順番に見ていく。

### 1. CLAUDE.mdでプロジェクトのルールを固定化する

一番効果が大きかったのはこれ。プロジェクト直下に`CLAUDE.md`を置くと、Claude Codeが起動時に自動で読み込んでコンテキストにする。毎回同じ指示（コーディング規約、禁止事項、テストの回し方）をチャットで打ち込む必要がなくなる。

```bash
# プロジェクトルートに雛形を作る
claude
> /init
```

`/init`を叩くと、リポジトリの構造を解析して`CLAUDE.md`の初稿を自動生成してくれる。あとは手で削って自分たちのルールに合わせていく。実際に自分が使っているCLAUDE.mdの中身はこんな感じだ。

```markdown
## Core Principles
- Simplicity First: 変更は最小限に。関係ないファイルを触らない
- No Laziness: 根本原因を直す。一時しのぎの修正はしない
- テストがあるコードは必ず実行してから完了報告する

## Workflow
- 3ステップ以上のタスクはPlan Modeで設計してから着手する
- ユーザーから修正が入ったら tasks/lessons.md に理由を書いて残す
```

ポイントは、グローバル設定（`~/.claude/CLAUDE.md`）とプロジェクト設定を分けること。個人の作業スタイル（サブエージェントを積極的に使う、無人運用時の安全ルールなど）はグローバルに、プロジェクト固有のルール（テストコマンド、ディレクトリ構造）はプロジェクト側に書く。これを分けておくと、複数プロジェクトを掛け持ちしていても指示のブレがなくなる。

### 2. カスタムスラッシュコマンドで定型作業を圧縮する

毎回同じような指示を打つ作業（コードレビュー観点の指定、デプロイ前チェックなど）は`.claude/commands/`にMarkdownで置いておくとスラッシュコマンド化できる。

```bash
mkdir -p .claude/commands
```

```markdown
<!-- .claude/commands/pr-check.md -->
PRを出す前に以下を確認して報告して:
1. git diff で意図しない変更が混ざっていないか
2. lintとテストが通るか
3. .env や認証情報がステージングされていないか
4. コミットメッセージが変更内容と一致しているか
```

これを置いておくと`/pr-check`で毎回同じチェックリストを走らせられる。自分で覚えておかなくていいのがいい。実務でよく使うのは「テスト実行→lint→git status確認」をワンセットにしたコマンドと、「デザインドキュメントとの整合性チェック」をワンセットにしたコマンドの2つ。

### 3. サブエージェントで調査とコーディングを分離する

大きめのタスクをこなす時、メインのコンテキストを調査ログで埋めたくない。`.claude/agents/`にYAMLフロントマター付きのMarkdownを置くとサブエージェントを定義できる。

```markdown
---
name: explore
description: 読み取り専用でコードベースを探索する。ファイル特定やシンボル検索に使う
tools: Read, Grep, Glob
---

コードを変更せず、質問に答えるための調査だけを行う。
```

実運用では「調査はサブエージェントに投げて要約だけ受け取る」「実装はメインで行う」という分業にしている。これでメインの会話が長くなりすぎず、コンテキスト圧迫によるパフォーマンス低下を防げる。並列で独立した調査を複数投げる時は、1メッセージの中で複数のAgent呼び出しをまとめて送るのがコツだ（順番に1個ずつ投げると、その分待ち時間が積み上がる）。

### 4. Hooksで「うっかり事故」を防ぐ

無人実行や自動化を絡めるようになってから一番怖いのが「意図しないコマンドが勝手に実行される」事故だ。`settings.json`にhookを書いておくと、特定のツール呼び出しの前後にシェルコマンドを挟める。

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "scripts/block-force-push.sh"
          }
        ]
      }
    ]
  }
}
```

`block-force-push.sh`の中で`git push --force`のようなコマンドを文字列マッチして、危険なら終了コード非ゼロで止める、という運用にしている。無人cronで動かす自動化ほどこの仕組みが効いてくる。人間がその場でレビューできない分、機械的にブロックする層を用意しておく必要がある。

### 5. Plan Modeで大きめのタスクは設計してから着手する

3ステップ以上かかりそうなタスク、アーキテクチャの判断が絡むタスクは、いきなりコードを書かせずにPlan Modeに入れている（Shift+Tabを2回押すと切り替わる）。Plan Modeでは実際のファイル変更が発生しないので、方針だけレビューして「これで進めて」と承認してから実装に入れる。

これをやらずにいきなり実装させると、途中で方針転換が必要になった時の手戻りが大きい。特に複数ファイルにまたがる変更や、既存の設計に手を入れる系のタスクほど、事前のすり合わせが効いてくる。

## 保存版：Claude Code実務Tipsチェックリスト

毎回思い出すのが面倒なので、自分用にチェックリスト化したものを置いておく。そのまま使ってもらって構わない。

| # | チェック項目 | やること | 効果 |
|---|---|---|---|
| 1 | プロジェクトにCLAUDE.mdがあるか | `/init`で雛形生成→手で調整 | 毎回の指示打ち込みが不要に |
| 2 | グローバル設定とプロジェクト設定を分けたか | `~/.claude/CLAUDE.md`と`.claude/CLAUDE.md`を使い分け | 複数案件でのブレを防止 |
| 3 | 定型作業をコマンド化したか | `.claude/commands/*.md`に切り出し | 毎回のタイプ量を削減 |
| 4 | 調査系タスクをサブエージェントに逃したか | `.claude/agents/*.md`で権限を絞ったエージェント定義 | メインコンテキストの温存 |
| 5 | 危険操作にhookを仕込んだか | `settings.json`の`PreToolUse`で拒否スクリプト | force push等の事故防止 |
| 6 | 大きめタスクはPlan Modeを通したか | Shift+Tab×2で切り替え | 手戻りの削減 |
| 7 | 無人実行の投稿・課金系操作に承認フローがあるか | 自動化は下書きまで、実行は人間承認 | 誤爆・意図しない課金の防止 |

特に7番は見落とされがちだが、SNS投稿やAPI課金が絡む自動化を組む時は「生成は自動、実行は承認」の一線を必ず引いておくべきだ。無人運用でここを飛ばすと、後から取り返しのつかない事故になりやすい。

## SES/フリーランスエンジニアとして見たAI活用の市場価値

ここまでは純粋な開発Tipsだったが、SESやフリーランスとして案件に出る立場から見ると、これらの運用ノウハウ自体が単価交渉のカードになる。

### 単価に直結するのは「使えること」ではなく「型化できること」

現場で見ていると、「Claude Codeを使ったことがある」エンジニアはもう珍しくない。差がつくのは、CLAUDE.mdやカスタムコマンドのようにチーム全体の生産性を底上げする「型」を持ち込めるかどうかだ。個人の作業が速いだけでは単価の説明材料として弱いが、「チームの開発フローにAI運用ルールを設計・導入できる」という実績は、SES契約でもフリーランス契約でも評価されやすいポイントになる。

### エンジニア キャリア ガイドとしてのAIスキル習得ロードマップ

SESからフリーランスへのキャリアパスを考える上で、AIツール活用は次のようなステップで習得していくのが現実的だと感じている。

1. **個人利用フェーズ**: Claude Codeを自分のタスクで使い、CLAUDE.mdやスラッシュコマンドで自分専用の型を作る
2. **チーム展開フェーズ**: 自分が作った設定・hookをチームの標準として共有し、レビューやCI運用に組み込む
3. **提案フェーズ**: クライアント先で「AI活用による開発フロー改善」を提案できるようになる

この3段階を経験しているかどうかは、エンジニア市場データ分析の文脈でも語られることが増えてきた領域で、契約更新や単価改定の交渉材料として持ち出しやすい。SES契約でスキルシートに「Claude Code運用設計」「AI活用による開発効率化施策」のような具体的な実績を書けるかどうかで、次の案件の選択肢の幅も変わってくる。

## まとめ

 Claude Codeを実務で使い倒すコツは、チャットで頑張って指示するのではなく、CLAUDE.md・カスタムコマンド・サブエージェント・hook・Plan Modeという「仕組み」に落とし込むことだ。この記事で紹介した設定はすべてそのまま動くものなので、まずはCLAUDE.mdを1つ作るところから試してみてほしい。

 そしてSES・フリーランスとして働く立場からは、AIツールを「使えること」で終わらせず、「チームに型として持ち込めること」まで踏み込むと、単価交渉やキャリアの選択肢に直結してくる。技術力そのものと同じくらい、こうした運用設計力が評価される時代になってきている。
